# Impossibility Engine — CLAUDE.md

An AI Dungeon Master for D&D 2024 on SRD 5.2.1. This file is the whole of
what an agent needs on every task: what the project is, the rules that may
never break, how the code is laid out, how work is verified, and which short
document to read before changing a subsystem. It is meant to be read in full.

`docs/IMPOSSIBILITY_ENGINE_DOCTRINE.md` outranks this file. Where they
disagree, the doctrine wins and this file is what needs correcting. Its core
line: **AI interprets possibility; the Engine adjudicates reality.**

## Inviolable rules

1. **The model never produces a number.** It states intent by calling a tool;
   the engine rolls, validates legality and returns the outcome; the model
   narrates what the event log says happened. Damage takes a `RollId` the
   engine issued; only `rolls.ts` stamps `engine`; the external-roll functions
   (`recordExternalD20`, `recordExternalDamage`) exist for a human DM and are
   never exposed to an AI one.
2. **`packages/engine` is pure.** No `Math.random`, `Date.now`,
   `crypto.randomUUID`, I/O, or content. ESLint enforces the first three; the
   sweep in `spell-schema.test.ts` enforces the last.
3. **State changes only through `GameEvent`.** `GameState` is `fold(events)`.
   Same seed and same log fold to a byte-identical state, forever.
4. **The engine holds no catalogue.** Spells, classes, features, species,
   backgrounds, feats, items, languages and alignments are *content*,
   supplied by the caller as a validated `Content` value. The SRD's
   catalogue is `@ie/content`; homebrew goes through the same door
   (`createContent` / `loadContent`). Adding content that uses mechanics the
   engine already has must not touch the engine.
5. **What a command reads from content is pinned into the events it emits.**
   A casting pins its area and numbers; an equip event pins the armour
   record. The fold never opens a catalogue, so replaying last year's log
   does not depend on this year's book. The two frozen fixtures predate
   pinning and are folded with the content they were written against
   (`fold(seed, events, legacy)`); nothing else is.
6. **Rules-legal refusals are values, not exceptions.** Return
   `err(code, reason)`; `needsContext(...)` when a fact is missing rather than
   wrong. Exceptions are for programmer error.
7. **Tests come first.** Write the failing test, watch it fail for the right
   reason, then implement. Never regenerate `packages/engine/fixtures/*.json`.
8. **Numbers live in `COVERAGE.md`**, regenerated by `npm run coverage` and
   diffed in CI. Do not put a count in prose.

## Architecture

```
React/Fastify/orchestrator (M2+, not built) ──► @ie/tools (not built)
                                                     │
      @ie/content  ──(a validated Content value)──►  @ie/engine  ──► @ie/srd, @ie/shared
```

| Package | Holds |
|---|---|
| `@ie/shared` | Branded ids, D&D vocabulary, the `Result` type (`ok` / `err` / `needsContext`) |
| `@ie/srd` | SRD 5.2.1 parsed into typed, schema-validated data: spells index, monsters, equipment |
| `@ie/engine` | The rules: dice, rolls, checks, attacks, damage, conditions, positioning, combat, casting, durations, rests, creation, the fold. Plus the **vocabulary** content is written in (`SpellDefinition`, `FeatureGrant`, …), the two validators (`spell-schema.ts`, `feature-schema.ts`) and the registry (`content.ts`) |
| `@ie/content` | The SRD catalogue as data: spell definitions, the twelve classes and subclasses, species, backgrounds, feats, items, languages, alignments. Built once into `SRD_CONTENT` through `createContent`, the same call homebrew uses |

Dependency direction is strict: content depends on engine; engine never
imports content. Engine tests that drive SRD spells import `@ie/content` as a
fixture, which is the only place that edge exists.

### How content reaches a command

- Commands that roll take a `Supply` — `{ issuer, rng, content }` — beside
  the state. Commands that only read content take `content` explicitly
  (`takeReady`, `equipItem`, `purchaseItem`, `eligibleTargets`, …).
- Creation takes content first: `createCharacter(content, choices, id)`,
  `advanceCharacter(state, content, id, advance)`.
- The fold takes none. `fold(seed, events)` is content-free for any log this
  engine writes.

### Engine layout

```
packages/engine/src/
  dice, rolls, roll-modifiers, checks, attack, bonuses   the D20 pipeline and typed damage
  conditions, vitals, standing, resources, rest, clock   creature state and what changes it
  positioning, combat, reactions, duration               space, the action economy, time
  spells, spell-definitions, spell-schema                casting records and the definition vocabulary/validator
  progression, feature-schema, origins, character        the class/feature vocabulary and the sheet
  content                                                the registry: createContent / loadContent / extendContent
  creation, multiclass                                   choices in, a validated character out
  commands/   one module per domain; commands.ts is the barrel
  fold/       one module per region of state; fold/apply.ts is the entry
  events.ts, state.ts                                    the GameEvent union and GameState
```

## Verification

```bash
npm install
npm run srd:ingest && npm run srd:index   # fresh clone only: generated SRD data is gitignored
npm test                                  # Vitest, all packages
npm run typecheck                         # tsc -b, then the tests
npm run lint
npm run coverage                          # regenerates COVERAGE.md; commit the result
```

Before pushing: all five green and `git diff --exit-code COVERAGE.md` empty.
CI runs the same on Node 22 and 24.

The load-bearing tests, so you know what a change can break:

- `scenario.test.ts` — a scripted four-round fight replayed byte-identically
  from its seed; the determinism ship criterion.
- `persistence.test.ts`, `persistence-2.test.ts` — two frozen logs must fold
  to the states they always folded to. A rules change that moves them is a
  migration and says so in the same commit.
- `content.test.ts` — a homebrew spell and a homebrew class, loaded from JSON
  text, created and cast through the public API with no engine change.
- `spell-schema.test.ts` (sweep) — no engine file names a catalogue id, a
  fixed spell grant, or a class; no command branches on a spell's name.
- `origin-and-feature-sweep.test.ts` (sweep) — the same of every species,
  background, feat and feature id, with the breaches it found held to the
  record so that fixing one fails until its entry goes.
- `invariants.test.ts` — every command is idempotent under its command id and
  asks rather than refuses when a fact is merely missing.
